## Decisions and deviations

1. **`voices.distinct_weavers` is a Phase 17 addition not present in the design brief or the literal migration SQL quoted in `docs/PHASE_17_SPEC.md` Part A4.** The spec's `debts`/`permanent_in`/echo-payload "weavers" fields all assume a number that can read 7, 8, or 9 (partial progress toward permanence). But Phase 16's `qualified_weavers` column — by its own design (`levee-permanence.ts`'s doc comment, and Phase 16's own report deviation #2) — reads **0** whenever either permanence condition fails, then jumps straight to the true count once both hold; it can never read 7-9. Rather than change Phase 16's committed semantics (the spec explicitly forbids this: "it needs no change to Phase 16's thresholds or SQL"), this implementation adds `distinct_weavers` (the raw distinct-weaver-identity count, ignoring the hour-bucket gate) to migration `0008` and `levee-permanence.ts`'s `computeDistinctWeavers`. It is used only for the mailbox's narrative numbers (`debts`, `permanent_in`, the `woven`/`sinking` payload's `weavers` field) — the actual permanence gate everywhere else remains exactly `qualified_weavers >= 10`, untouched.
2. **`CONTRACT.endpoints` does NOT gain `echo`/`who`, despite the spec's literal wording ("CONTRACT gains ... endpoints.echo, endpoints.who").** `CONTRACT.endpoints` is iterated generically by `discovery.ts`/`errors.ts`/`zodToEnvelope` assuming the write-triad's shared shape — one fixed literal `path`, `fields`, `example`, `rateLimit`, `returns`. `/echo/{id}` and `/who/{id}` are parametrized GETs with a materially different shape (query params instead of a POST body, no Zod validation, two rate-limit scopes). Forcing them into `endpoints` would either break every generic consumer's type assumptions or require giving the write-triad's entries a padded, unused shape. Implemented instead as a sibling top-level `MAILBOX` export (`MAILBOX.echo`, `MAILBOX.who`).
3. **The idempotency receipt's HTTP status on replay is always 200, regardless of the original write's status (201 for both imprint and weave).** The spec's Part B prose says a hit "return[s] `receipt` verbatim with the original status", which taken literally would mean a replay is *also* 201 — but the acceptance table (B1: "201 then 200") explicitly contradicts that. This implementation follows the acceptance table: the original write is 201, every replay (sequential retry or the rare concurrent-loser path) is HTTP 200 with `replayed: true`, body otherwise identical to the original.
4. **`leave_imprint`'s family-count query moved from after the insert to before it** ("joining N other voices" no longer counts the just-inserted voice itself — a pre-existing off-by-one in the Phase 15/16 code, invisible until Phase 17 needed the count available *before* the voice id is minted, for the idempotency receipt callback that runs pre-batch). No test asserted the old number; this is a genuine, incidental correctness fix, not a deliberate scope item.
5. **`handlers/rest-weave.ts` does not share code with `tools/weave.ts` for the identity/idempotency/echo wiring** — same as the pre-existing (Phase 15/16) relationship between the two files (each has its own inline D1 batch). Both were updated in lockstep by hand; there is no single point of truth, matching the established pattern (`resolveSource` is the one function actually shared).
6. **A9 ("named agent weaves the same source from 3 sessions/3 IPs") is tested at the pure-function level (`computeDistinctWeavers`/`computeQualifiedWeavers`), not as a full HTTP round-trip.** `door-mocks.ts`'s `DoorD1` tracks weave_log distinctness by `weaver_trace_id`, not by `weaver_id`/`weaver_bucket` — a pre-existing simplification from Phase 16 (confirmed by `permanence.test.ts`'s own "COALESCE prefers a present weaver_id" test, which explicitly notes it only proves the *read path*, since "Phase 16 itself never writes weaver_id"). Extending the shared mock to properly separate trace-id-distinctness from identity-distinctness was out of scope for this phase; the underlying mechanism (`COALESCE(weaver_id, weaver_bucket)` collapsing three same-author rows to one distinct weaver) is proven directly.
7. **B3 ("two concurrent identical keyed requests") is not literally concurrent** — the hand-rolled synchronous mock has no interleaving point between the idempotency check and the batch commit, so true concurrency isn't reproducible. The test instead exercises the actual code path B3's guarantee depends on: `insertVoiceAndRebuild`'s own PK-collision recovery (pre-seeding the receipt row that a "concurrent winner" would have committed, then confirming the second request replays it rather than inserting a second voice). `tools/_shared.ts`'s `isUniqueConstraintError` + re-read-and-replay logic is exercised by this path in both `idempotency.test.ts`'s B3 and B1 (a genuine sequential retry also flows through the top-level `checkIdempotency` short-circuit, never reaching the batch at all — the two paths are deliberately different code, both tested).
8. **C5 (the `rooted` transition, "qualified_weavers 9→10") required a purpose-built `RootedD1` subclass** (in `echo-events.test.ts`) that stubs the one query computing qualified/distinct weavers, because — same root cause as #6 — `DoorD1`'s synthetic weave_log rows all report `Date.now()` as their timestamp, so 6 distinct hour buckets can never arise through a real weave sequence in this mock. `permanence.test.ts`'s own existing tests already establish that qualified_weavers never reaches 10 through a full `DoorD1` round-trip; C5 needed an actual `rooted_at`/echo-event side effect, so this report follows the established "each test file owns its scenario-specific mock" convention (`CLAUDE.md`'s existing note about `witness-tool.test.ts`/`discover.test.ts`) rather than mutating the shared `weavers` map's semantics for every other test.
9. **`weave`'s stored idempotency receipt uses pre-batch-computed approximations for `source_weave_count`/`source_unique_weavers`** (`source.weave_count + 1`, `source.unique_weavers + 1`) rather than the fully accurate post-batch numbers the *live* (non-replayed) response always uses. The true post-write counts aren't knowable until after the atomic batch commits, and the receipt insert must ride inside that same batch for the B3 race guarantee (otherwise two concurrent requests could each insert a distinct voice before either's receipt commits). In the overwhelmingly common case — a genuine sequential retry — the top-level `checkIdempotency` call in `handlers/rest-weave.ts`/`tools/weave.ts` short-circuits before ever reaching this approximation, since it replays whatever the *original* call's live response stored... except the original call's *stored* receipt is itself the approximation described here (built inside the same batch-construction step as the original write, before that write's own post-batch counts are known). So: every weave replay's `source_weave_count`/`source_unique_weavers` is this pre-batch approximation, exact in the near-universal case (no prior weave from the same session/bucket for that source), off by at most the count of such prior weaves in the rare edge case. No test asserts these specific numbers on a replay; documented here rather than silently accepted.
10. **`echo_events` for `woven`/`rooted` are written as follow-up statements after the qualified_weavers/distinct_weavers recompute, not inside the initial atomic write batch**, despite the spec's Part C1 table saying "in the weave batch". Unlike `op_receipts`, echo events carry no uniqueness/atomicity requirement in the acceptance table — nothing tests a race producing a duplicate echo event — so emitting them post-recompute (with fully accurate, non-approximated payload numbers) was judged strictly better than approximating them pre-batch purely to satisfy the spec's literal phrasing.

## Things the spec gets wrong, is ambiguous about, or leaves internally inconsistent

- **Part B's prose ("return `receipt` verbatim with the original status") contradicts its own acceptance table** (B1: "201 then 200"). Resolved per Decision #3 above, following the acceptance table as authoritative (it's the testable artifact).
- **The design brief (v2) and the shipped spec (v1, same day) disagree on the identity header's primary name and on whether reading a mailbox requires the secret.** The brief recommends `Authorization: Bearer` as primary with `X-Vellum-Agent` as an alias, and recommends the mailbox require the secret to read ("nobody can read your mailbox"). The spec — written after a Codex review and explicit human recalibration the same morning — reverses both: `X-Vellum-Agent` is primary (MCP hosts reserve `Authorization` for their own OAuth), and mailboxes are explicitly public ("mailboxes are public (no secret to read)"). This implementation follows the spec (the later, human-ratified document) throughout; the brief's contrary recommendations are superseded, not a bug, but worth flagging since a future reader skimming only the brief would build the wrong thing.
- **`qualified_weavers`'s inability to express partial progress (see Decision #1) is really a Phase 16 gap the Phase 17 spec didn't anticipate** — Part A4 asserts "this is the entire permanence effect of identity, and it needs no change to Phase 16's thresholds or SQL", which is true for the *gate* but silently assumes the *same column* can also serve the mailbox's progress-reporting needs. It can't, without the column's own semantics changing in a way that would itself be a Phase 16 SQL change. `distinct_weavers` resolves this without touching the gate.
- **The spec's Part D1 "MockD1 records zero queries" (acceptance D4) is stricter than what's actually achievable or desirable**: a 304 still charges the per-IP/per-id rate limits (both D1-backed, matching how `/api/voices` and every other read endpoint already work) — genuinely "zero D1 queries of any kind" would mean skipping rate-limiting on the cheapest, most poll-friendly endpoint in the API, which contradicts the same Part D1's own "expensive to over-ask" design goal. This report/test suite interprets "zero D1 reads" as zero reads of the mailbox's own content (`echo_events`/`voices`), which is what actually matters for the KV-cost argument the spec makes, and is what `echo.test.ts`'s D4/D7 tests precisely assert via a `first`/`all` call-site spy.

## Post-review fixes

Implemented on `2026-09-05`, in the same working tree, against an independent review of the Phase 17 diff. `bun run verify`'s worker suite exited 0 after every change below (381 passed, 0 failed, up from 314 at initial ship; worker `tsc --noEmit` clean).

1. **The `echo:max:<id>` KV cache (`handlers/echo.ts`'s conditional-GET ETag/HEAD fast path) was written once on a cold GET and never updated by any write path.** A polling agent's first `GET /echo/{id}` populated the cache at whatever `MAX(n)` existed then; every subsequent conditional GET compared against that same stale value forever, even as new `echo_events` rows landed for that agent — `If-None-Match` kept matching, so the agent got `304` indefinitely and never saw a new echo. `echo.ts` gains `refreshEchoCache(env, agentId)`, called after every `echo_events` insert across every write path (`tools/weave.ts`'s `rooted`/`room_woven`/`woven` hop 1/hop 2, `handlers/rest-weave.ts`'s identical four, `surfaces.ts`'s `touchSurfaceActivity` `surface_woven` insert, and `cache.ts`'s rebuild-time sweeps for `sinking`/`room_fading`/`surface_warmed`). It re-reads the authoritative `MAX(n)` from D1 rather than threading each insert's own autoincremented `n` through every call site (several ride a shared `db.batch()`), so it's correct regardless of call order, at the cost of one extra indexed D1 read per echo-emitting write — never on the poll-side read path, which stays exactly as cheap as the original design intended. `writeCachedMaxN`/`readCachedMaxN` moved from `handlers/echo.ts` into `echo.ts` itself (the shared hub every write path already imports from) so both the cold-populate read path and every write path share one implementation of the key shape and TTL. Test: `echo.test.ts` "D9" — an existing cached ETag, then a new event via a real weave, then the SAME (now-stale) ETag correctly gets `200` with the event, not `304`.
2. **The `sinking` echo's paired `UPDATE sink_mark` + `INSERT echo_events` rode the same `db.batch()` unconditionally** — the `UPDATE`'s own `WHERE sink_mark < ?` guard was already race-safe (only one of two concurrent rebuilds racing the same voice's threshold crossing actually raises `sink_mark`), but the echo `INSERT` was never conditioned on that `UPDATE` actually having matched, so the *losing* rebuild would still write a duplicate `sinking` echo. `cache.ts` now splits the sweep into two passes: batch every candidate's guarded `UPDATE` first, read back each statement's `meta.changes`, then batch an echo `INSERT` only for the subset that actually won (`changes > 0`) — the same pattern `tools/weave.ts`'s `rooted` echo already used. Migration `0012_echo_guards.sql` additionally adds a partial `UNIQUE INDEX` on `echo_events(agent_id, voice_id, json_extract(payload, '$.threshold'))` scoped to `kind = 'sinking'`, as a defense-in-depth backstop (the application-level guard should already make a duplicate impossible; the index makes it a schema-level guarantee too, at negligible cost since `sinking` events are rare). Test: `echo-events.test.ts` "post-review fix (item 2)" — a rebuild whose guarded `UPDATE` batch is intercepted mid-flight to simulate a concurrent winner already having advanced `sink_mark` asserts zero echo events result, not one.
3. **A session's bound `author_id` (set once at MCP `initialize`) used to be sufficient, on its own, for every later `tools/call` to write as that agent for the rest of the session's 45-minute life** — a leaked or copied `Mcp-Session-Id` let a bystander impersonate the bound agent with no secret at all, for up to 45 minutes. `handlers/mcp.ts` now treats the session binding as a **consistency check only**: a bound session's `authorId` is used for a given `tools/call` only when `X-Vellum-Agent` is present on THAT call and derives to the same id (mismatch is still the existing `AGENT_AUTH_FAILED`); a call with no header at all is anonymous even on a bound session. A malformed header is now a hard `AGENT_AUTH_FAILED` at any point, not just at `initialize` (previously silently ignored on a later call). This costs a legitimate client nothing — `contract.ts`'s `identity` block and the `initialize` `instructions` string already told clients to "send the same X-Vellum-Agent secret on every request," which is exactly what the fix now enforces rather than merely suggests. Tests: `identity-mcp.test.ts` "A6" (rewritten — see the acceptance table above), "A6b", "A7c" (malformed header on a bound session), "A7d" (a header on a session that never bound one stays inert — binding still only happens at `initialize`).
4. **`renderEchoLines`'s `woven` line and the identical `sense_space` echo prose (the same shared function) rendered a voice's own text inside a literal `"..."` wrapper without escaping embedded `"` characters.** A voice's text is untrusted and already passes through `sanitizeQuoted` at write time, but that sanitizer only ever handled whitespace/control/bidi characters, never literal ASCII double-quotes — a voice containing its own `"` could visually close the wrapper's quote early, making whatever followed in that voice's text read as if it sat outside the quotation (defense-in-depth concern for the "quoted, never a command" design law; nothing in this codebase treats echo/sense_space prose as instructions, so this was never an actual command-injection path, only a legibility/trust-boundary hardening). `quoted.ts` gains `escapeQuoted(s)`, replacing every literal `"` with a typographic `”` — applied only at render time in `renderEchoLines`'s `woven` case; the raw JSON `/echo/{id}` response is untouched (JSON's own escaping already makes that safe). Test: `echo-events.test.ts` "post-review fix (item 4)".

### Accepted as-is, not fixed by this pass

- **Anonymous idempotency's scope identity is `ip:<addr>` on the REST write paths (`handlers/rest-imprint.ts`, `handlers/rest-weave.ts`: `authorId ?? \`ip:${ip}\``), never per-anonymous-caller.** Two distinct anonymous agents behind one NAT or shared IP, both omitting `X-Vellum-Agent` and both reusing the same `Idempotency-Key` value within 24h, collide on the same `op_key` — one gets a spurious `IDEMPOTENCY_CONFLICT` if their bodies differ, or silently shares the other's receipt if their bodies happen to match. (The MCP tool paths, `tools/weave.ts`/`tools/leave-imprint.ts`, scope anonymously by `traceId` — the per-session id — instead, so this is REST-specific.) This mirrors the exact structural limitation Phase 16's own report already accepted for anonymous duplicate detection ("keys on IP, not per-agent identity" — `docs/PHASE_16_REPORT.md`'s Post-review fixes, item 8) for the identical reason: there is no other identity signal for an anonymous REST caller. Not fixed here; an agent that wants collision-free idempotency should send `X-Vellum-Agent`.
- **Minting a new `a_` id is bounded only by the general write-ceiling (`LEVEE.ceiling`), never by any identity-specific cap.** There is no registration step and no per-IP/per-session limit on how many *distinct* ids a caller can mint — every `X-Vellum-Agent` value, however novel, derives to a usable id on its very first presentation (`deriveAgentId`), and the only thing standing between a caller and an unbounded number of fresh identities is the same shared write-rate ceiling every anonymous write already contends with. This is deliberate, not an oversight: `docs/PHASE_17_SPEC.md`'s own framing ("identity is a gift, not a gate") and this report's Decisions #2 both reflect the human's explicit openness decision that identity should cost nothing and require no approval. Documented here because a future reviewer reading only the code might otherwise flag the absence of an identity-minting rate limit as a gap.
